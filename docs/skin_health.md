## 1. 背景

现有 pipeline（`infer_csv_scratch.py`）已经能从 IMU 数据里识别出"抓挠"这一行为片段（起止时间、置信度）。这份文档要解决的问题是：把离散的抓挠事件流，转成 PM 文档定义的 Scratch Burden Score 和 C0/C1/C2 三档护理建议，并且验证/校准里面所有的经验参数。

工作分两块，互相独立：

- **A. 趋势报告**：把抓挠事件按 PM 文档字段规范聚合成日/周数据，供内部分析和后续产品展示用
- **B. Scratch Burden Score + 基线**：按 PM 定义实现评分逻辑，重点是补全"个人基线"的具体算法，并对所有经验参数做数据验证

## 2. Scratch Burden Score（按 PM 文档 V0.4 定义）

### 2.1 评分结构

PM 文档明确**不建议直接向用户展示 0–100 分**，只在算法内部计算，对外只展示 C0/C1/C2 三档：

```
Scratch Burden = 变化幅度(0-30) + 聚集程度(0-20) + 持续程度(0-20) + 正常行为影响/中断(0-30)
```

四个维度**全部是相对信号**（相对基线、相对当日模式、相对日间连续性、相对正常作息），**没有独立的绝对频率/时长阈值分项**——这一点比此前讨论过的"Whistle式分级+ChatGPT草案"更合理：那两版都是"60%权重挂绝对阈值+10%权重挂基线偏离"的结构，导致本身抓挠基线很低的狗，哪怕相对变化很大也很难触发高分（详见本文档旧版讨论，已被此结构取代）。PM 这版把绝对量纲完全排除在计分公式外，只用来做"聚集/中断"里的辅助判定条件（比如"1小时≥5次"），从根上避免了那个问题。

**红旗信号（Red-flag override）**：不参与加权平均，而是"命中即强制升级"规则，避免严重症状被其他低分维度稀释：

| 触发条件 | 效果 |
|---|---|
| 相对基线 > 3倍 | 变化幅度直接30分 |
| 当日聚集时段 ≥ 3个 | 聚集程度直接20分 |
| 连续偏离基线 ≥ 3天 | 持续程度直接20分 |
| 连续/高度聚集抓挠达到1分钟 | 直接触发红旗，"长时间抓挠事件" |
| 满足多种正常行为反复中断（≥2次）或持续抓挠≥60秒 | 正常行为影响直接30分 |

四个分项各自的红旗都命中30/20/20/30满分时，总分会自然落在 C2 区间；单一维度触发红旗不代表总分一定进 C2，需要看加总后落在哪个区间。

### 2.2 分数等级

```
C0 On Track：           0 ≤ C < 30
C1 Watch Closely：     30 ≤ C < 50
C2 Vet Check Recommended：50 ≤ C ≤ 100
```

对外文案只用 "detected / pattern / change / may be worth checking / consider contacting a veterinarian" 这类措辞，禁止 "diagnosed / confirms / has an infection / is in pain"。

### 2.3 个人基线——PM 文档留白，算法侧需要给出具体方案

V0.4 更新记录里写着"删除个人基线定义"，但 `Baseline_scratch_event_count`、`Baseline_scratch_total_duration_sec`、`baseline_delta_pct` 这些字段仍然是核心输出的一部分——**基线怎么算，目前是产品没有定、需要算法侧落地的部分**。

沿用此前的设计（基线窗口跳过最近7天，避免持续性异常被自我吸收进基线）：

```
X_base = median(X_{d-21}, ..., X_{d-8})   # 排除最近7天，取此前14天中位数
X_7d = 加权均值(X_d, X_{d-1}, X_{d-2}, ...) # 越近权重越高
```

`X_d` 可以是事件数、总时长，或两者的组合，取决于 §2.1"变化幅度"部分要求的"双值取大"（事件数和时长两个维度分别算倍数，取较高分）。

**双门槛判断**（PM文档表一）：同时满足"相对倍数"和"最小绝对增量"才计分，且倍数计算时分母最低按3处理，避免基线为0/1/2时倍数被无限放大：

| 基线变化 | 次数最小绝对增加 | 时长最小绝对增加 | 相对倍数 | 偏离分 |
|---|---|---|---|---|
| 无明显变化 | <3次/24h | <1分钟/24h | 不判断倍数 | 0 |
| 轻微变化 | ≥3次/24h | ≥3分钟/24h | 1.3~1.5倍 | 5 |
| 明显变化 | ≥5次/24h | ≥5分钟/24h | 1.5~2倍 | 10 |
| 显著变化 | ≥10次/24h | ≥10分钟/24h | 2~3倍 | 20 |
| 显著变化 | ≥20次/24h | ≥15分钟/24h | >3倍 | 30 |

刚绑定设备、基线数据不足时不打分，标注"基线正在建立中"，不用群体均值强行替代。

### 2.4 聚集程度、持续程度、正常行为中断

三块直接按 PM 文档定义实现，不重复展开公式，关键取值汇总见 §4（作为待验证参数清单的一部分）：

- **聚集程度**：1小时内（有效佩戴）抓挠事件≥5次记为1个聚集时段，当天聚集时段数决定得分
- **持续程度**：要求"当日变化幅度≥10分"才计入连续天数；某天数据不足12小时暂停计数（不重置不增加）；连续两个数据不足日则终止本次持续周期；最长回溯7天
- **正常行为中断**：核心是"抓挠相关睡眠中断"的判定——睡眠≥5分钟→抓挠事件≥3秒（或60秒内累计≥6秒）→中止后清醒≥3分钟才算一次中断；未重新稳定入睡（≥5分钟）的多次抓挠合并为同一次中断；相邻中断事件间隔≤5分钟也合并

## 3. 事件与字段定义（对齐 PM 文档 schema）

### 3.1 抓挠事件定义

| 概念 | 定义 |
|---|---|
| 抓挠动作（stroke） | 后肢完成一次"抓触—回摆"的周期，不单独展示 |
| 抓挠事件（event） | 开始：连续≥2个周期性抓挠动作，或信号持续≥1秒，且置信度达到起始阈值、设备有效佩戴；持续：间隔≤3秒的短暂停顿仍算同一事件；结束：连续>3秒未检测到抓挠，或转换为其他行为，或设备脱落/松动 |
| 有效佩戴（valid wear） | 设备正确佩戴、信号质量达标的时长 |

> **"3秒"是产品建议的算法参数，不是临床标准**——PM文档明确要求后续用视频标注数据在 2秒/3秒/5秒 之间比较事件级 Precision/Recall 和用户感知一致性，选出最优值（见 §4 第1项）。

### 3.2 核心输出字段

按 PM 文档 §8 统一字段命名，不要另起一套命名（避免跟下游接口/前端对不上）：

**事件级**：`event_id, pet_id, device_id, label_id, start_time, end_time, duration_sec, confidence, confidence_band(high/medium/low), signal_quality, wear_state(worn/off-body/charging/uncertain), model_version, algorithm_version, source, suppression_reason, user_feedback, local_day, timezone`

**日聚合**：`event_count, total_duration_sec, valid_wear_minutes, coverage_rate, baseline_delta_pct, trend_direction(up/stable/down/insufficient_data), night_ratio, data_quality_flag(good/partial/insufficient)`

**抓挠专属**：`scratch_event_count, scratch_total_duration_sec, scratch_duration_per_wear_hour, sleep_disruption_count, Baseline_scratch_event_count, Baseline_scratch_total_duration_sec, baseline_delta_pct, scratch_attention_level(C0/C1/C2)`

`confidence`/`data_quality_flag` 不参与打分计算，单独展示——数据不足时显示"佩戴不足/正在学习"，禁止用0代替无数据（PM文档 §15 明确要求）。

## 4. 待验证参数清单（算法工程侧的核心工作）

PM 文档里大量参数标注了"建议初始值""产品算法配置值，不是临床标准"，这些都需要拿真实标注数据验证/调整，而不是直接采信。按优先级排列，并给出用现有工具怎么验证：

| # | 参数 | 文档给的初始值 | 怎么验证 |
|---|---|---|---|
| 1 | 事件合并间隔 | 3秒（同类信号间隔≤3秒合并） | 用 `event_eval.py` + `run_review_bins_all_days.sh` 的 `MERGE_GAP` 参数分别跑 2s/3s/5s，比较事件级 Precision/Recall/F1e，选最优值。README 里现有说明"3s会把约一半真实事件错误合并"是基于1s场景的旧结论，这次要针对抓挠场景专门重新测 |
| 2 | 事件结束判定 | 连续>3秒未检测到抓挠 | 同上，与合并间隔一起联调，两者未必要用同一个数值 |
| 3 | 聚集阈值 | 1小时内≥5次抓挠事件记为1个聚集时段 | 需要先有一批多日标注数据，统计"聚集时段"出现频率是否合理（比如是否所有狗几乎每天都触发，或几乎没有狗触发——任一极端都说明阈值不合适） |
| 4 | 持续程度门槛 | 当日变化幅度≥10分才计入连续天数 | 依赖 #6 基线偏离分档是否合理，两者要联合验证 |
| 5 | 睡眠中断判定六项阈值 | 稳定睡眠≥5分钟、有效抓挠≥3秒、中止间隔≤30秒、清醒≥3分钟、合并间隔≤5分钟、夜间有效佩戴≥4小时 | 需要能可靠区分"睡眠/清醒/抓挠"三种状态的标注数据，是本方案里对数据要求最高的一块，建议先验证睡眠状态识别本身的准确率，再验证中断判定逻辑 |
| 6 | 基线偏离分档（双门槛表） | 见 §2.3 表格 | 先用现有多日数据跑一遍 `X_base`/`X_7d` 计算，看实际计算出来的偏离分布落在哪些档位，是否需要调整档位边界 |
| 7 | C0/C1/C2 总分边界 | 0-30 / 30-50 / 50-100 | 待上述子项都验证完、有真实评分分布后再定，不建议现在就锁死 |
| 8 | 红旗信号阈值 | 3倍基线、1分钟持续抓挠、≥3天持续偏离等 | 用历史确诊/复查记录（如果有）反推这些红旗阈值的误报率，没有确诊标签时先看触发频率是否合理 |

> 验证时注意 PM 文档 §13.2 的要求：训练集/验证集/测试集必须按犬只隔离，不能同一只狗跨集合。

### 4.1 合成数据已经发现的一个公式级问题（不是参数调优，是逻辑缺口）

用 `src/eval/gen_synthetic_scratch_scenarios.py` 跑合成数据时发现：**§2.3 双门槛公式里"分母最低按3计算"这条规则，会让低基线狗的适度绝对增加永远算不出分**。

具体机制：基线≈0的狗，分母被下限保护成3；要让 `ratio = current / 3 ≥ 1.3`（最低档"轻微变化"的倍数门槛），当天事件数必须 ≥4。也就是说，一只原本几乎不抓挠的狗，哪怕稳定维持在**每天3次**的新水平（`3/3=1.0倍`，达不到1.3倍门槛），无论持续多少天，变化幅度分永远是0——这正是我们最早讨论"前14天0、后14天3"那个例子的翻版，只是这次是在PM的正式公式里复现出来的，不是我们自己假设的。

这不是"参数取值需要调"的问题（调阈值治标不治本），而是双门槛公式本身对"极低基线+适度绝对增加"这类组合结构性不敏感。建议跟产品侧同步这个发现，讨论方案，比如：
- 分母保护值改成更小的数（如1），让极低基线下更小的绝对增加也能反映出倍数变化；或
- 单独给"绝对增加"设一个更低的独立触发门槛（不要求同时满足倍数），比如"基线≤2次的狗，绝对增加≥3次直接给最低档分而不看倍数"；或
- 干脆认为"低基线狗的适度抓挠增加"本来就不该被列为需要关注的信号，维持现状——但这需要产品/兽医角度确认，不是算法能单方面决定的

### 4.2 用现有工具做同样的验证——不要止步于合成数据

上面这个发现是靠合成数据跑出来的，但合成数据只能验证"打分逻辑本身对不对"，不能替代真实数据验证。§4表格里那些参数（事件合并间隔、聚集阈值等）必须用真实标注数据+`event_eval.py`/`run_review_bins_all_days.sh` 验证，见 §8。

## 5. 验收标准（摘自 PM 文档 §12，抓挠相关部分）

| 指标 | 门槛 |
|---|---|
| 事件级 Precision（抓挠/甩头） | ≥90%（8月31日目标85%，10月13日目标95%，见文档 §4 标签表） |
| 事件级 Recall（抓挠/甩头） | ≥80% |
| 附加要求 | 高Precision优先；夜间和长毛犬需要单独出报告，不能只看整体平均 |

犬级宏平均（先按每只犬算指标再平均）是强制要求，避免数据量大的犬只主导整体指标。

## 6. 外部参考资料（作为参数校准的旁证，非设计主依据）

### Whistle FIT — [PMC10445133](https://pmc.ncbi.nlm.nih.gov/articles/PMC10445133/)

分级阈值（已用 Pruritus VAS 验证）：Infrequent 0–52秒/天、Occasional 53–119秒/天、Elevated 120–299秒/天、Severe >300秒/天（对应群体50/85/97分位）。这是目前能找到的、经过临床量表验证的绝对秒数参考，可以用来交叉检查 §4 里那些"次数/时长最小绝对增加"门槛（比如"≥3分钟/24h"这类值）在真实场景下是不是合理量级。

告警机制是"7天滚动均值所在分级，相比前一天上升≥1档触发"，比 PM 文档这套连续型评分更简单，但已经在7000+只狗、20个月的真实数据上验证过效果（告警上线后"4周内就诊"占比从35.2%升到54.1%，OR=1.63, p<0.0001，对既往无皮肤病记录的狗效果最明显）。如果后续验证发现 PM 这套更精细的评分体系在实际效果上并不比"简单分级+环比"更好，这是一个更简单的备选方案。

底层用 FilterNet 深度学习模型，与本项目 README 参考文献引用的一致。

### Vetrax — [What's Normal When It Comes To Scratching?](https://vetrax.com/whats-normal-when-it-comes-to-scratching/)

超过8万犬日的运营数据：日均抓挠约100秒，个体范围从<10秒到1500秒+。**样本可能有选择偏差**（用户本身可能因为担心皮肤问题才用监测设备）、"犬日"不等于独立犬只样本、原文未公开分位数和设备准确率——只能当粗略的量级参考，不能当临床阈值。核心价值是反复强调"What's normal for *this* dog"，支持 PM 文档"个人基线优先于群体均值"（§15 竞品对比一节也有同样表述）的设计方向。

## 7. 工程实现与合成数据验证

### 7.1 代码

- `src/eval/scratch_burden.py`：SBS 打分引擎。输入统一的事件表（`pet_id, start, end, duration_sec`）+ 每日有效佩戴时长表，输出每只狗每天的四项子分、红旗、总分、C0/C1/C2。包含 `load_events_from_infer_json()`，可以直接读 `infer_csv_scratch.py` 产出的 `*_infer.json`（`scratch_segments` 字段），衔接真实数据不需要再写一遍格式转换
- `src/eval/gen_synthetic_scratch_scenarios.py`：生成9种场景的合成事件数据，跑一遍引擎，打印/保存每只"狗"每天的完整打分明细，用于验证机制本身有没有按预期工作（不是验证抓挠识别准确率，那部分依赖真实标注数据，见 §4）

运行方式：
```bash
python src/eval/gen_synthetic_scratch_scenarios.py
# 输出打印到终端 + 保存到 data/synthetic_skin_health_sbs_report.csv
```

### 7.2 合成数据覆盖的场景

| 场景 | 目的 |
|---|---|
| 低基线狗稳定波动 | 验证正常情况下不误报，全程应为 C0 |
| 从0陡增到3次/天（此前讨论过的0→3例子） | 验证低基线狗的相对变化能否被捕捉——**结果：捕捉不到，见 §4.1 的公式缺口** |
| 逐日缓慢恶化 | 验证"持续程度"分项能否正确累积、红旗能否在持续偏离后正确触发 |
| 高基线狗小幅波动（PM文档示例五：30→35） | 验证双门槛能正确判定"不算变化"，不误报 |
| 单日高度聚集 | 验证"聚集程度"分项 |
| 夜间反复抓挠致睡眠中断 | 验证"正常行为影响"分项和中断判定逻辑 |
| 单次连续抓挠超60秒 | 验证"长时间抓挠"红旗能否正确触发 |
| 设备脱落/未佩戴的缺失日 | 验证缺失日被正确标记为 `insufficient`，不参与基线计算、不被当成"0次=正常" |
| 刚绑定设备（历史<21天） | 验证冷启动阶段不强行打分 |

### 7.3 结果摘要

除 §4.1 提到的低基线问题外，其余场景表现符合预期：
- 逐日恶化场景里能清楚看到 `delta_score` 逐日上升、`persistence_score` 在连续偏离≥3天后达到20分上限，并在偏离幅度超过3倍基线时正确触发 `baseline>3x` 红旗、总分跳到 C2
- 高基线小幅波动场景全程为0分，双门槛判断本身没问题（问题只出在基线接近0的边界情况）
- 聚集、长时间抓挠、缺失日、冷启动这几个场景都按预期触发对应分项/标记
- 夜间中断场景发现一个需要留意的边界情况：算法按 PM 文档 §5"事件按开始所在日期归属"的规则实现，跨零点的同一个"夜晚"会被切成两个日历日分别计算中断次数（比如23点和次日02点的两次抓挠会被算进两天），这是符合文档字面规则的行为，但实际是否符合"一晚的睡眠质量"这种产品语义，需要跟产品侧确认是否要改成按"睡眠周期"而不是"日历日"聚合夜间指标

### 7.4 跟真实数据的衔接

你这边持续抓取的真实数据积累到可用量级后，衔接路径是：

1. 用现有 `infer_csv_scratch.py` 批量跑出 `*_infer.json`
2. 用 `scratch_burden.load_events_from_infer_json()` 读进来，跟合成数据用同一套 `run_pipeline()` 计算
3. 重点看两件事：(a) §4.1 那个低基线公式缺口在真实狗身上是不是真实存在的问题（合成数据只是理论推演，真实狗的基线分布、事件粒度可能让这个问题不明显，也可能更严重）；(b) §4 表格里的经验参数（3秒合并、1小时5次聚集等）在真实数据上算出来的日常分布是否合理
