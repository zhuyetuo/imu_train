# 佩戴状态检测：松动检测 + 未佩戴/静置检测

## 1. 背景与目标

项圈松动或被摘下时，IMU 数据要么已经不能反映狗的真实行为（松动导致额外晃动混进信号），要么根本不是狗产生的（设备静置/充电时的信号）。这两种情况都不该喂进主行为分类模型，也不该计入抓挠/睡眠/活动等下游统计——这正是 PM 文档（Wardyn V0.4）§6 `LOOSE_COLLAR` 和 `wear_state` 字段（`worn/off-body/charging/uncertain`）要覆盖的范围，也是 `docs/skin_health.md` §3.2 里 `wear_state`/`data_quality_flag` 字段依赖的上游判断。

两个检测是独立的判断，不是同一个模型的两个输出：

1. **松动检测**：判断"戴着，但没戴稳"——项圈相对颈部的贴合角度在动
2. **未佩戴/静置检测**：判断"根本没戴在狗身上"——设备放在桌上/正在充电/被人拿着

都是**规则/信号处理判断**，不是训练出来的分类模型，理由跟 SBS 的红旗信号是一个道理：这类判断需要强可解释性、能让人一眼看出"为什么判定松动/未佩戴"，而不是黑盒模型给一个置信度了事。

## 2. 松动检测

### 2.1 思路

PM 文档原话："在适合判断的运动状态下（如仅在持续稳定行走或小跑20～30秒时启动判断），检测到设备相对于犬颈部出现持续、重复的异常摆动或方向不稳定"。

关键约束：**只能在稳定步态窗口里判断**，脱离稳定的参考运动就没法区分"晃动是项圈松了"还是"狗本来就在做别的动作"。

具体实现（`src/data/wear_state.py::tilt_drift`）：
1. 复用现有 `gravity_align.py::raw_tilt`，算出窗口内逐样本的 pitch/roll
2. 把这段"稳定步态"窗口切成若干2秒子段，算每个子段的平均朝向
3. 子段间平均朝向的标准差，就是"漂移/晃动程度"——项圈越松，狗每完成几个步态周期，项圈相对颈部的贴合角度就越容易悄悄变化，子段平均朝向会比正常佩戴时更分散
4. 超过阈值（`LOOSE_WOBBLE_STD_THRESHOLD_RAD`，当前 0.06 弧度，**待真实数据校准的经验值**）判定该窗口"松动"

### 2.2 聚合成事件

按 PM 文档规则：10分钟滑窗内松动信号累计超过3分钟，记1次松动事件（`aggregate_loose_events`）。松动事件期间的抓挠/活动/睡眠数据不采信——这个逻辑直接对接 `docs/skin_health.md` 里的 `data_quality_flag`/`wear_state`，不需要另起一套。

### 2.3 判断"是否处于稳定步态"这个前置条件谁来给

`tilt_drift` 本身不判断是否在走路，需要外部传入 `is_stable_gait` 标记。生产环境里这个标记应该来自主行为分类模型输出的"行走/小跑"标签（连续20~30秒），松动检测是下游的第二遍处理，不是独立于行为识别之外的东西。

## 3. 未佩戴/静置检测

### 3.1 核心思路：心跳/呼吸微振动

脖子佩戴天然贴近颈动脉/气管，狗即使睡得再沉，心跳和呼吸引起的微幅振动理论上也会在加速度信号里留下痕迹——这是比"运动能量高低"更本质的"活体佩戴 vs 静置物体"判据。设备摘下放在桌上/充电时，不会有这种生物周期信号。

**产品定位很明确：这是过渡方案。** PM 文档给的原始思路是"温湿度持续偏离个体正常佩戴微环境"，用温湿度传感器判断未佩戴——但当前硬件阶段还没有温湿度传感器，产品也还没到成品阶段。所以现阶段只能靠 IMU 单独判断，温湿度上线后应该作为辅助信号提升置信度，而不是替代 IMU 判断。

### 3.2 具体实现

`src/data/wear_state.py`：

1. **`is_macro_still`**：先判断宏观运动能量是否接近0（加速度模长标准差低于阈值）——只有这类窗口才需要往下判断，明显在动的窗口直接认定"佩戴中且活动"，不用跑生物信号检测
2. **`bio_signal_energy`**：对宏观静止的窗口，用四阶巴特沃斯带通滤波器过滤到 `[0.15Hz, 3.0Hz]`（覆盖狗的静息呼吸频段 ~0.25-0.5Hz 和静息心率频段 ~1-2.3Hz，体型越小心率越快，留了余量），算带通后信号的方差
3. 方差超过阈值（`BIO_SIGNAL_ENERGY_THRESHOLD`，**待真实数据校准的经验值**）→ 判定 `worn_resting`（佩戴中静息/睡眠）；否则 → 判定 `off_body_or_static`

### 3.3 目前区分不了未佩戴 / 静置 / 充电

`off_body_or_static` 是一个合并状态——单靠这套心跳/呼吸信号判断，只能回答"设备现在是不是不在狗身上"，答不出"是被摘下放桌上、还是在充电"。这三者要细分，要么等温湿度传感器上线（充电时设备温度会有特征性变化），要么额外接入充电状态的硬件信号（比如充电检测电路本身的状态位，如果设备本身能读到这个信号，那是最直接的，不需要靠IMU猜）。**这个合并暂时是设计上可接受的**，因为下游用途（要不要把这段数据算进行为统计）只需要知道"不在狗身上"，不需要知道具体是哪种"不在"。

## 4. 已知风险和局限（都需要真实数据才能回答，不是靠推理能确定的）

| # | 风险 | 说明 |
|---|---|---|
| 1 | **信噪比够不够** | 心跳/呼吸振动幅度本身很小，隔着毛发、皮肤、项圈松紧程度，加速度计能不能实际测到，纯经验问题。合成数据验证只证明了"检测机制在信号存在时能正确工作"，不能证明真机上这个信号真的存在、真的能被测到 |
| 2 | **采样率** | 现有 pipeline 训练用的是16Hz降采样后的数据，奈奎斯特频率8Hz，理论上覆盖呼吸/心率频段没问题；但降采样本身会损失细节，未佩戴检测**可能需要用降采样前的原始高采样率数据算，不跟主行为模型共用一条数据流**——这是架构上的一个决策点，需要确认设备端/传输链路能不能提供未降采样的原始流给这个检测用 |
| 3 | **松动检测和未佩戴检测的交互** | 项圈一旦松了，就算狗醒着趴在原地，心跳/呼吸振动的传导也可能因为贴合度变差而检测不到——"松动+静息"可能被误判成"未佩戴"。理论上可以联合判断（松动检测器也在报警的情况下，"无生物信号"更可能是松动导致而非真的没戴），但这个交叉逻辑目前只是设想，需要真实数据验证两种情况的实际区分度 |
| 4 | **充电/被人拿起时的振动噪声** | 充电底座本身可能有轻微电气振动，人拿起把玩设备也会产生运动，这些跟"静置"的信号特征可能不一样，甚至可能被误判成有生物信号——现在的合成场景没有覆盖这些情况，需要真实数据补充测试 |

## 5. 工程实现与合成数据验证

### 5.1 代码

- `src/data/wear_state.py`：核心检测逻辑。`detect_loose_window`/`aggregate_loose_events` 做松动检测；`classify_wear_state`（内部调 `is_macro_still`/`bio_signal_energy`）做未佩戴/静置检测。所有阈值常量都标了 `TODO_CALIBRATE`
- `src/eval/gen_synthetic_wear_state_scenarios.py`：生成5种场景的合成原始IMU数据，跑一遍验证检测机制本身对不对

运行方式：
```bash
python src/eval/gen_synthetic_wear_state_scenarios.py
```

### 5.2 合成数据覆盖的场景与结果

| 场景 | 目的 | 结果 |
|---|---|---|
| 项圈逐渐变松的30分钟行走 | 验证松动检测能不能捕捉到"渐进式"松动，而不是只能识别"一开始就很松" | PASS：前8分钟无触发，第8分钟和第18分钟各检测到1次松动事件（对应松动程度累计超过阈值的时间点），符合"前期不触发、后期稳定检测到"的预期 |
| 全程佩戴稳固的对照组行走 | 验证正常情况下不误报 | PASS：全程0次松动事件 |
| 长时间佩戴中睡眠 | 验证有生物信号时正确判定 `worn_resting`，不会被误判成未佩戴 | PASS：全程120个窗口全部判定 `worn_resting` |
| 设备摘下放置/充电 | 验证无生物信号时正确判定 `off_body_or_static` | PASS：全程120个窗口全部判定 `off_body_or_static` |
| 完整一天的状态切换（睡眠→活动→摘下充电→活动→睡眠） | 验证状态切换的连续性和正确性 | PASS：精确观察到 `worn_resting→worn_active→off_body_or_static→worn_active→worn_resting` 的完整切换序列，切换点跟场景设计的时间点吻合 |

**重要说明**：合成数据里心跳/呼吸信号的振幅、噪声底是为了让检测机制"可演示"而选的参数（约100倍信噪比差距，见 `gen_synthetic_wear_state_scenarios.py` 里的注释），**不代表真机的真实信噪比**。这次验证只证明了"信号处理链路本身没写错——有信号能检出来，没信号不会误报"，不能证明真机上这个信号真的强到能被测到（对应 §4 风险1）。

### 5.3 跟真实数据的衔接

真实数据积累后，第一件要确认的事情就是 §4 的风险1：真机加速度计能不能实际测到心跳/呼吸引起的微振动。具体做法：找一段已知"设备正在佩戴、狗在安静休息"的真实数据，跑 `bio_signal_energy()`，跟一段已知"设备确实被摘下静置"的真实数据对比，看这两类数据的能量值有没有像合成数据里那样出现数量级差异——如果真实数据里两者差异很小甚至重叠，说明这条路径在当前硬件上不可行，需要回退到"只用宏观运动能量+时间段先验"的弱化方案，等温湿度传感器上线再补强。

## 6. 开放问题

1. 未降采样的原始高采样率数据，能不能在这个检测模块里单独取到？如果只能拿到16Hz降采样后的数据，需要重新评估检测效果（见 §4 风险2）
2. 松动检测和未佩戴检测的联合判断逻辑（§4 风险3）要不要现在就设计，还是先看真实数据里这两种情况的实际冲突频率再决定
3. 温湿度传感器上线后，怎么跟现有 IMU-only 的判断做融合——是简单的"任一信号判定未佩戴就采信"，还是需要更细的置信度加权，这个可以等硬件确定后再设计，不用现在预判
4. `LOOSE_WOBBLE_STD_THRESHOLD_RAD`、`BIO_SIGNAL_ENERGY_THRESHOLD`、`MACRO_STILL_ACC_STD_THRESHOLD` 这几个阈值都需要真实数据重新校准，合成数据里选的值只是让机制可演示，没有物理意义上的准确性
