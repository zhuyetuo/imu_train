# 没有陀螺仪的版本：acc 三轴 + pitch/roll（5 通道，113 维）

陀螺仪很费电。这个目录回答：**把它砍掉，行为识别掉多少。**

全是新增文件，仓库原有的任何东西都没有动。

---

## 一条命令

用法跟 `train_custom.sh` **完全一样**，把脚本名换掉就行：

```bash
bash acc3/train_acc3.sh --date "2026_8_11-2026_8_27_raw" --source_hz 50 --hz 16 \
  --extra_date "2026_8_28_imu1_bb:50" \
  --extra_date "2026_8_28_imu2_bali:50" \
  --extra_date "2026_8_28_imu3_lulu:50" \
  --extra_date "2026_8_28_imu4_xiaoman_unwear:50" \
  --label_mode majority --window_s 1 --stride_s 0.5 \
  --missing_strategy drop_window \
  --skip_syn --model rf --clean --feat_workers -1
```

训完直接打印「基线 vs 只有加速计」的对比表。

## 通道：3 + 2，不是 3

一个 3 轴加速度计设备，能给出来的输入是 **5 列**：

```
0:3  acc_x, acc_y, acc_z   传感器，重力对齐后
3:5  pitch, roll           派生 —— arctan2 从 acc 三列算出来的，不是传感器
```

`pitch/roll` 为什么要单独留一列：预处理里的**重力对齐**会把每个窗口整体旋转，
让平均加速度指向 +Z（好让特征跟项圈戴歪多少无关）。副作用是**每个窗口的
平均倾角都被归零，「躺着 / 坐着 / 站着」这个绝对姿态整个没了**。所以在对齐
**之前**先把倾角算出来单独存两列。`gravity_align.py:raw_tilt` 的 docstring
里写明了这个顺序。

这两列只需要加速计：

```python
pitch = arctan2(-ax, sqrt(ay² + az²))
roll  = arctan2(ay, az)
```

---

## 为什么不重跑预处理，直接把陀螺仪那三列砍掉

因为**重力对齐的旋转矩阵只从加速度计算出来**：

```
gravity_align.py:28   g_est = acc.mean(axis=0)      ← 只看 acc
gravity_align.py:57   out[:, :3] = (R @ acc.T).T
gravity_align.py:59   out[:, 3:6] = (R @ gyr.T).T   ← 只是把同一个 R 也用在陀螺仪上
```

所以 `[acc 对齐后, pitch, roll]` 这五列，**有没有采过陀螺仪都是同一个数**——
不是「约等于」，是逐位相同（`selfcheck5.py` 第 ① 条验的就是这个）。

好处是基线和 3 轴版**用的是同一批窗口**，差值只能来自通道。重跑预处理的话
窗口划分的随机性会变，差值里就混进了别的东西。

### 一个**不**等价的地方

`--missing_strategy drop_window` 会丢掉含 NaN 的窗口。有些窗口是**因为陀螺仪
那几列断联**才被丢掉的——真的只有加速度计的设备上，那些窗口会留下来。

所以这份数据的窗口集合 = 基线的窗口集合，比真 3 轴设备**偏少一点**。
对「砍掉陀螺仪影响多大」这个问题来说这是好事（两边窗口完全一样）。
要量那部分影响得从 CSV 重跑，那是另一件事。

## 特征：113 维，不是 95 维

`src/ml/features.py` 的 `_extract_one` 里，全局特征、模长特征、jerk 特征
**全都挂在 `window.shape[1] >= 6` 底下**。直接喂 5 通道进去只有 95 维，
少掉的是：

| 少掉的 | 维数 |
|---|---|
| acc 三轴模长（时域 11 + 频域 8） | 19 |
| acc jerk 模长（时域） | 11 |
| SMA_acc + acc 三轴相关系数 | 4 |

**这 34 维只需要加速计就能算。** 那个门槛存在的原因是「gyro 的模长/SMA 要用
3:6 列」，不是「acc 的算不出来」。用 95 维去回答「砍掉陀螺仪影响多大」，
会把**实现上少算的**和**传感器上少的**混在一起，得到一个偏低的数。

所以 `features5.py` 按 5 通道重新拼了一遍：

```
时域(5 个通道 55) → 频域(只有 acc 三轴 24) → SMA+三轴相关 4
→ acc 模长(时域+频域 19) → acc jerk(时域 11)   = 113
```

频域为什么跳过 pitch/roll：跟仓库那份同一个理由——姿态角不是振荡信号。

**一行新公式都没有。** 11 个时域统计、8 个频域统计、SMA、相关系数、模长、
jerk 全部直接调 `src/ml/features.py` 里那几个函数，只是换了拼接顺序。

### 113 维正好是 193 维的一个子集，逐位相同

把 8 通道那 193 维里所有名字带 `gyr` 的删掉，剩下**正好 113 维，顺序一致、
数值逐位相同**（`selfcheck5.py` 第 ②③ 条拿仓库那份代码当参照验过）。

这个性质有两个用处：

1. **验证**：新写的特征代码有没有跟训练侧分家，能直接对出来。
2. **上线**：推理时照常算 193 维，然后按下标取那 113 列 —— 5 通道的模型
   **不需要一条新的预处理链**。下标存在 `ml_rf.json` 的 `feature_select` 里。

## 训练流程整段复用 train.py

`train_acc3.py` 只做一件事：把 `train.extract_features` 换成 5 通道那份。
标签重映射、类别分布、特征缓存、验证集兜底、评估、保存 —— 全是
`src/ml/train.py:main()` 的原代码。抄一份的话重映射那套迟早分家，
而分家之后两个模型「指标能比，但比的不是同一件事」。

替换完会**当场核一遍**（真跑一个探针窗口，看维度是不是 113）。
没替上不会报错：5 通道喂给 8 通道那份会给 95 维，训练照跑、指标照出，
只是少了那 34 维 —— 指标偏低，而偏低的原因看不出来。

## 文件

| 文件 | 干什么 |
|---|---|
| `features5.py` | 5 通道的特征提取，113 维。所有统计量都调仓库那份，没有新公式 |
| `make_acc3_npz.py` | 8 通道 npz → 5 通道（砍掉 3:6 的陀螺仪） |

## 跟 `acc_only/` 的关系

`acc_only/` 是**同一个问题的另一种做法**：保留 8 通道形状、把陀螺仪置零，
得到 193 维（其中 80 维是常数）。信息量跟这里的 113 维**完全一样**，
好处是现有服务一行都不用改，代价是推理时白算 80 维。

这个目录（`acc3/`）是真的 5 通道、113 维，更接近一个 3 轴设备实际的样子。
**优先用这个。**
