# 皮肤评级算法工程方案——用统计/工程标准方法替代SBS手调公式

> 这份文档是对`model_roadmap.md`的修正和补充。之前的讨论默认"SBS继续用，
> 在它之上叠加变点检测/BHM"，但重新审视后发现**SBS本身的打分层（四个子分数
> 加权+红旗覆盖）就有工程问题，不是一个值得长期背负的地基**。这里给出替代
> 方案、分阶段实施计划，以及跟现有代码的过渡方式。

## 1. SBS现在的打分层，具体问题在哪

`scratch_burden.py`里`score_day()`往下的逻辑（`score_delta`/`score_cluster`/
`score_persistence`/`score_interruption`四个子分数 + 红旗覆盖）存在三个
实际的工程缺陷，不是风格偏好问题：

1. **没有统一目标函数**：四个子项的权重（10/20/30这些分值）是拍出来的，
   没有一个"总分越准确"的量化定义，没法用网格搜索/贝叶斯优化自动调参——
   因为"调到多少算更好"这件事本身没有可优化的目标。
2. **硬编码例外分支太多**：红旗触发时直接覆盖分数（`delta_score = 30`、
   `cluster_score = 20`），这类特殊分支越多，代码的状态空间越大，越难
   写全测试用例——`BASELINE_DENOM_FLOOR`那次的bug就是这类硬编码逻辑的
   典型副作用（一个不起眼的`max(baseline, 3)`保护逻辑，静默把低基线狗的
   分数清零了很久没发现）。
3. **没有标准的评估流程**：现在"改完代码跑10个合成场景肉眼看结果对不对"
   （`scenario_gallery.md`），没有train/val/test划分，没有统一量化指标
   （AUC/F1/校准误差），这在有真实标签之后必须升级，合成场景验证只能
   保证"逻辑没崩"，不能回答"这组参数是不是真的准"。

`scratch_burden.py`里**特征提取那部分是没问题的、要保留**：`daily_features()`
（按天聚合次数/时长/聚集数/夜间占比等特征）、`load_events_from_infer_json()`
（从推理结果读事件）这些是纯粹的数据处理，跟"怎么打分"无关，之前的合成场景
验证本质上也是在验证这部分逻辑（聚集判定、睡眠中断判定这些是特征工程，不是
打分公式，是靠谱的）。**要换掉的只是"特征算出来之后怎么变成一个总分/等级"
这一层**。

## 2. 替代方案：分阶段用标准统计/机器学习方法

| 阶段 | 时间 | 方法 | 为什么选它 |
|---|---|---|---|
| 前期 | 现在-9月（无标签） | **稳健Z分数**（中位数+MAD）或 **CUSUM/EWMA控制图** | 都是统计过程控制/经典统计里的标准工具，参数少（1-2个），有理论指导怎么选参数（不是拍脑袋），不需要监督标签 |
| 中期 | 9-11月（几十条兽医标签） | **逻辑回归** | 权重从数据里学出来，不是人拍的；回归系数带显著性检验，能看出哪些特征真的有用；依然可解释，能直接讲给兽医听 |
| 后期 | 12月+（标签量更大） | **梯度提升树(GBM)** + SHAP解释 | 处理非线性关系，前期的BHM冷启动先验/变点检测信号可以作为特征喂进来，一套模型吸收多个信号源，而不是养多套独立评分系统 |

### 2.1 前期：稳健Z分数 / CUSUM-EWMA

**稳健Z分数**：挑1-2个信息量最大的特征（建议先用"日总抓挠时长"，`skin_health.md`
里已经论证过这是Whistle FIT等文献验证过最有信息量的单一指标），用**中位数+MAD**
（median absolute deviation，对异常值比均值+标准差更抗噪）算个人基线，
`z = 0.6745 * (当天值 - 中位数) / MAD`（0.6745是让MAD在正态分布假设下跟标准差
可比的标准换算系数），`|z| > 2.5~3` 判定异常，只有一个可调参数（阈值），
统计意义明确（Z分数直接对应正态分布下的显著性水平，比如z=2.5对应约99%分位）。

**CUSUM/EWMA控制图**：如果Z分数对渐进式恶化不够敏感（Z分数是逐日独立判断，
不看趋势），上CUSUM（累积和控制图）——制造业质量控制里几十年的标准工具，
专门设计给"尽快检测均值发生了偏移"这个任务，核心公式：

```
S_t = max(0, S_{t-1} + (x_t - target - k))
```

`k`是"允许的漂移容忍量"，`h`是报警阈值，两者都有ARL（平均运行长度，Average
Run Length）理论公式指导怎么选，给定"能容忍百分之多少的假阳性率"和"想多快
检测出多大的偏移"，可以反推出k和h该设多少——这是有教材、有公式的参数选择，
不是凭感觉试出来的。

冷启动期两个方法都一样可以用Whistle FIT文献阈值兜底，跟SBS现在的思路兼容，
只是把"怎么打分"这层从四个加权子项换成这一两个更简单、更标准的统计量。

### 2.2 中期：逻辑回归（有真实标签之后）

一旦有几十条兽医真实标注（正常/关注/异常），在`daily_features()`已经算好的
特征（次数/时长/聚集数/夜间占比/是否触发睡眠中断等）上做**监督学习**：

```
P(异常) = sigmoid(β0 + β1*次数 + β2*时长 + β3*聚集数 + β4*夜间占比 + ...)
```

用`sklearn.linear_model.LogisticRegression`（建议加L1正则，`penalty='l1'`，
天然做特征选择，没用的特征系数会被压到0）。这一步能直接回答一个SBS现在
答不出来的问题：**四个子分数里哪些真的有预测力**——如果某个特征的回归系数
在统计上不显著，说明SBS里那个子项当初的设计假设（比如"聚集程度"）可能根本
没有实际区分力，该砍掉而不是继续背着。

评估上开始用标准流程：分层抽样切train/val/test（狗与狗之间要分开切，不能
同一只狗的数据同时出现在train和test，否则会信息泄漏），指标用AUC（排序能力）
+ 校准曲线（预测概率是不是真的对应实际发生率，医疗场景校准误差比纯AUC更重要，
"模型说70%可能异常"应该真的对应70%左右的实际异常率，不能只关心排序对不对）。

### 2.3 后期：GBM + 多信号融合

标签量更大之后（比如几百条），逻辑回归的线性假设可能不够用，升级成
`lightgbm`/`xgboost`，用SHAP值保留可解释性（每个预测能拆解成"次数贡献了+15%，
夜间占比贡献了-3%"这种，不会因为换了模型就丢失可解释性）。这时候前面攒的
BHM冷启动先验估计、CUSUM报警信号，都可以作为**输入特征**喂给这一个模型，
而不是并行维护SBS、BHM、CUSUM三套独立输出再手动决定听谁的——**一套模型
吸收多个信号源**是更干净的架构，避免"SBS说C1、BHM说异常、CUSUM没报警，
产品该展示哪个"这种没有单一决策来源的混乱局面。

## 3. 跟现有代码怎么过渡

| 模块 | 现状 | 处理方式 |
|---|---|---|
| `scratch_burden.py`里`load_events_from_infer_json()`/`daily_features()` | 特征提取，逻辑没问题 | **保留**，新方法直接复用这层输出的特征表 |
| `scratch_burden.py`里`compute_baseline()`（14天中位数基线） | 基线概念是对的，稳健Z分数需要同样的"中位数基线" | **保留并扩展**，加一个MAD的计算（现在只算了median，没算MAD） |
| `scratch_burden.py`里`score_delta`/`score_cluster`/`score_persistence`/`score_interruption`/红旗覆盖 | 四个加权子项+硬编码例外，问题所在 | **逐步替换**：先在旁边新增`robust_zscore.py`跑双轨（SBS继续生产、新方法先影子模式验证一致性和跟兽医的吻合度），确认新方法不差于/优于SBS之后再切主线，不是一刀切下掉重写 |
| `BOOTSTRAP_ELEVATED_SEC_PER_DAY`等Whistle FIT绝对阈值 | 冷启动期兜底 | **保留**，新方法一样需要冷启动兜底，逻辑复用 |
| `daily_skin_report.py`/`skin_health_daily_template.md` | 兽医对照日报机制 | **保留**，这是不管用什么打分方法都需要的验证基础设施，且是中期逻辑回归训练数据的唯一来源 |
| `scenario_gallery.md`合成场景 | 验证SBS机制用的 | 场景定义本身（10种情况：稳定/突增/渐进恶化/聚集/夜间中断等）**可以复用**去验证新方法在同样场景下表现是否合理，不用重新设计测试用例，只是换一套打分逻辑跑一遍对比 |

**具体切换节奏建议**：8月-9月先把稳健Z分数/CUSUM实现出来，跟SBS**并行跑**
（两边都生成日报，都不告诉兽医是哪个方法出的分，看哪个跟兽医独立判断更吻合），
9月底看双轨对比结果决定要不要把生产日报切到新方法；旧的SBS代码不用立刻删，
降级成"备用/交叉验证"角色，直到新方法稳定运行1-2个月没有明显问题再考虑清理。

## 4. 跟`model_roadmap.md`/`deployment_plan_2026.md`的关系

- `model_roadmap.md`列的BHM/变点检测/GP/生存分析这几个候选方向，结论不变——
  这份文档只是把"规则/统计基线"这一格的具体实现，从"SBS的四加权子项公式"
  改成"稳健Z分数/CUSUM"，`model_roadmap.md`里提到的"变点检测"其实就是这里
  的CUSUM，两份文档在这一点上是一致的，不冲突。
- `deployment_plan_2026.md`的月度节奏（8月4只狗到12月50只狗、11月BHM
  go/no-go决策点）不变，只是"日常评分用什么方法"这一项从"SBS"更新为
  "稳健Z分数/CUSUM（前期）→ 逻辑回归（中期，标签攒够之后）"，BHM在这个
  节奏里仍然只负责冷启动辅助这个窄范围，跟主评分方法用什么无关。
