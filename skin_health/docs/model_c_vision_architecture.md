# 皮肤健康评估——模型C（视觉皮肤检测）方案

> 这是一份新增方案，跟`two_stage_rf_architecture.md`定义的模型A/B架构
> **并行独立**，不修改、不影响模型A/B现有的代码和行为。模型A/B处理的是
> IMU项圈的行为信号（抓挠/睡眠/活动），模型C处理的是照片/视频的视觉信号
> （皮肤看起来怎么样），两条通道各自独立产出结论，互相印证、不互相替代。

## 一、要解决的问题

狗狗皮肤问题（过敏、皮炎、真菌感染等）早期表现主要是抓挠行为异常，但
单纯"抓得多不多"不足以判断严重程度和要不要就医——这是模型A/B已经在
解决的问题（用学习出来的权重代替PM固定权重公式，见
`two_stage_rf_architecture.md`）。

但行为信号本身有天花板：**抓挠次数/时长只能反映"狗有没有在挠"，反映
不了"皮肤实际长什么样"**。这两件事不是total 1:1对应的关系——用户提出
的两个典型反例：

- 一天抓挠100次，但拍照看皮肤其实还好（可能是习惯性抓挠、或者问题还
  没发展到肉眼可见的阶段）
- 一天抓挠0次，但拍照看皮肤已经明显有问题（可能是狗因为疼痛反而不敢
  抓、或者问题出在不太会引起抓挠反应的部位）

这两种"信号不一致"的情况，只看IMU行为信号是发现不了的，需要一路独立
的视觉信号才能补上。

## 二、总体架构：模型A与模型C并行

```
IMU项圈数据(抓挠/睡眠/活动)          狗狗皮肤照片/视频(用户主动拍摄上传)
        │                                      │
        ▼                                      ▼
   【模型A】行为严重度分类器              【模型C】视觉皮肤病灶检测
   （已有，不改动，见                     （新增，YOLO目标检测）
   two_stage_rf_architecture.md）
        │                                      │
   输出：C0/C1/C2                        输出：检测框列表[{类别,置信度,bbox},...]
   （每天自动跑，被动持续信号）              + 汇总视觉严重度 V0/V1/V2
                                          （用户主动触发，稀疏信号）
        │                                      │
        └──────────────┬───────────────────────┘
                        ▼
              【交叉验证/一致性检查】（见第四节，本方案的核心价值点）
              C档位 vs V档位是否一致——不一致的情况重点标记，
              不是简单取二者均值/谁权重高糊弄过去
```

**模型A原有的C1/C2触发问答→模型B综合判断这条链路完全不变**（见
`two_stage_rf_architecture.md`），模型C是在这条链路之外新增的第三路
独立信号，不是插进A→B中间的一环。模型C要不要、什么时候并入模型B的
输入特征，是后续单独评审的事，本方案不擅自决定（见第六节）。

## 三、模型C细节设计

### 3.1 输入

- 单张照片，或者视频抽帧后按单张照片处理
- MVP阶段不强制要求拍摄角度/部位标注，后续如果发现同一类病灶在不同
  角度/部位下检测效果差异大，再考虑要不要加这层辅助信息

### 3.2 检测目标类别（候选，需要跟兽医确认，不是算法组自己拍板）

初步候选类别，参考PM问答题库(`questionnaire_paper_form.md`)里皮肤颜色
/皮损/秃毛分布/秃毛面积几题已有的分类体系，尽量让类别名称/严重度分档
能跟这几题的选项对上：

- 红肿（对应问答"皮肤颜色"里鲜红/发红那几档）
- 皮损/糜烂/结痂（对应问答"皮肤是否完整"那几档）
- 色素沉着/黑色油脂（对应问答"皮肤颜色"里D/E两档）
- 脱毛区域（对应问答"秃毛分布/秃毛面积"两题）
- 正常皮肤（可选，作为负类/背景类，不一定需要专门检测框）

跟问答选项对齐是为了让接口将来兼容"模型C自动判断代替/辅助人工填这几
题问答"这个可能性——**这不是本方案现阶段的目标**，只是设计检测类别
时顺手考虑一下，避免以后要用的时候发现类别体系完全对不上、要推倒重来。

类别体系最终要不要按这个候选定，需要兽医专业判断（比如"红肿"和"发炎"
临床上是不是同一个东西、要不要拆细），也要考虑标注实际可行性——分得
太细会导致某些类别的样本量永远凑不够，训不出来。

### 3.3 输出格式

- **原始输出**：YOLO标准检测框格式，每个框`{class, confidence, bbox}`
- **汇总输出**（给交叉验证/展示层用）：从检测框列表算出一个"视觉严重度
  分"V0/V1/V2。MVP阶段建议先用**简单规则**，不是一上来就训一个"检测框
  →严重度"的学习式融合模型——这层映射需要严重度标签，在真实标签攒够
  之前，先用类似这样的规则挡着（具体阈值待定，示例）：
  - 检测到"糜烂"类别 → 直接V2（红旗类，参考模型A/PM方案里"某个维度
    严重到直接跳档"的同一个设计思路）
  - 检测到"红肿"/"结痂"，且检测框面积占画面比例超过阈值 → V1
  - 都没有 → V0

  等真实标签+使用数据积累到一定量，再评估要不要把这层规则换成可学习
  的模型，这是后续独立的决定，不是本方案现在就要锁死的。

### 3.4 训练数据/标注流程

- **数据来源**：用户主动拍照/视频上传——跟问答一样是"触发型"稀疏信号，
  不像IMU数据是每天自动持续采集的
- **标注工具**：复用现有Label Studio基础设施（这个仓库的IMU标注流程
  已经在用，见`src/review_to_labelstudio.py`），但要换成目标检测的
  标注模板（画框+选类别），不是现在时间序列标注用的
  `timeserieslabels`模板——这是Label Studio项目配置层面的新增，不影响
  现有IMU标注项目的配置
- **标注人员**：现有标注团队（周蕾/刘雪飞等）经过培训后可以标框，专业
  判断（比如"这算不算红肿"）建议兽医抽检复核——跟IMU那边"ML自动预
  标注+人工复查"是同一个思路，模型C训出第一版之后也可以反过来先出
  预标注框，人工只需要修正而不是从零画，降低标注成本

### 3.5 模型选型

- YOLO系列（具体版本比如YOLOv8/v11按当时生态成熟度选，不在方案里锁死
  具体版本号），理由：目标检测任务的成熟方案，单张图片推理快，如果
  以后产品要做到"拍完立刻出结果"这种体验，也有本地/边缘部署的空间
- 训练框架：`ultralytics`（业界标准，跟仓库里其他模型一样是Python生态，
  不引入额外的技术栈负担）

## 四、跟IMU信号（模型A）的交叉验证机制——本方案的核心价值点

这是用户明确提出的诉求，也是模型C存在的核心意义之一：**不是简单选一路
信号当权威、另一路当参考，而是把"两路信号是否一致"本身当成一个有价值
的信息去用**。

### 4.1 为什么需要交叉验证，不是简单相信某一路

- **IMU信号的局限**：抓挠行为可能是习惯性的（跟皮肤是否真的有问题弱
  相关），也可能狗在皮肤已经很严重时反而因为疼痛不敢碰、不怎么抓挠
- **视觉信号的局限**：拍摄角度/光线/毛发遮挡可能让镜头前"看起来还好"
  但实际皮肤下已经有问题；用户主动拍照的频率也不稳定，不像IMU是被动
  持续采集的

两路信号各自都有盲区，只有两路都看、且专门去看"哪里对不上"，才能补上
单路信号覆盖不到的情况。

### 4.2 一致性判定的具体设计

- **一致**：C档位（模型A）和V档位（模型C）方向一致（比如都轻、都重）
- **不一致**（重点标记案例）：
  - **IMU重、视觉轻**：抓挠多但照片看着没事——可能是"习惯性抓挠"，也
    可能是早期还没发展到肉眼可见的阶段，值得跟踪（比如过几天视觉信号
    是不是也开始变重了，验证"IMU比视觉更早预警"这个假说）
  - **IMU轻、视觉重**：抓挠少但照片明显有问题——可能是狗因为疼痛反而
    不抓、也可能问题出在不太会引起抓挠反应的部位，这种情况**建议提高
    就医优先级**，不能因为IMU信号正常就掉以轻心

### 4.3 在数据标注流程节点的应用

用户原话提到的具体用法：在积累训练数据、给样本打真值标签的阶段，把
"IMU当天的C值/事件统计"和"当天/临近几天拍摄照片对应的V值"放在**同一张
核对表**里给兽医看——兽医打真值标签时能同时看到两路信号，遇到"不一致"
的样本优先人工复核、多看几眼。这类样本对训练模型C（以及未来可能出现的
"模型A和模型C怎么融合"这层）价值更高，比"两路信号一致、随便标一下就
过"的样本信息量大，标注排期上可以优先处理"不一致"的样本。

这个交叉验证机制本身**不需要等模型C训练完才能用**——只要有V档位（哪怕
现阶段是人工标注的、不是模型预测出来的）和C档位（模型A已经在产出），
这个对比逻辑就能先跑起来，可以在真实模型C训练完成之前，先拿人工标注的
V值实测一下这套交叉验证流程设计得对不对（见第七节MVP建议）。

## 五、跟现有模型A/B的关系（明确边界，避免误解成"要改A/B"）

- **不修改**`rf_features.py`/`scratch_burden.py`/`train_rf_model_a.py`/
  `train_rf_model_b.py`——模型C是全新增加的第三条通道，模型A/B的代码和
  行为完全不变
- 现阶段模型C的输出（V档位/检测框）**不会自动喂进模型B的S档位预测**
  ——模型B目前的输入定义（`rf_feature_spec.md`+`questionnaire_feature_
  spec.md`）不变。等模型C真的训练出来、验证过确实有增量价值，要不要把
  V档位或者检测框相关特征当成模型B的新增输入，是后续单独评审的事，本
  方案不在这里预先决定
- 产品体验上，模型C可以**独立展示**（"拍照检测"这样一个独立入口），
  不需要绑定在"抓挠异常触发问答"这条流程里——用户可以随时主动拍照
  上传，这也是模型C跟模型A/B"被动触发"不一样的地方：它是主动补充信号，
  不是被动触发链条里新增的一环

## 六、未决问题/需要确认（不擅自决定）

- **检测类别体系最终定义**：需要兽医专业意见校准，不能纯靠算法组自己
  定；也要考虑标注实际可行性，类别分得太细会导致某些类别样本量凑不够
- **数据来源**：现在有没有已经积累的狗狗皮肤照片/视频？还是要从零开始
  收集？这决定了项目的启动节奏
- **V档位在产品UI上怎么呈现**：C/S/V三个档位都展示给用户？还是要综合
  成一个最终结论？这是产品设计问题，不是这份算法方案本身要回答的，但
  需要产品侧尽早介入讨论，避免算法这边先把接口设计死了产品又要改

## 七、MVP阶段建议范围（避免一次性铺太大）

1. 先定好检测类别体系（第3.2节），去跟兽医对齐
2. 用少量已有数据（如果有的话）或者现场采集一小批（比如20-30张有代表
   性的照片）验证类别体系可行性，不是一上来就要成百上千张
3. Label Studio加一个目标检测标注模板，标注团队试标一批，看类别体系
   顺不顺手，需要不需要合并/拆分某些类别
4. 用一小批数据先训一版原型模型（哪怕效果一般），主要目的是跑通
   "数据→标注→训练→推理"这一整条链路，这个阶段不追求准确率
5. 交叉验证机制（第四节）的"不一致"检测逻辑本身不需要等模型C训练完
   ——只要有V档位（哪怕是人工标注的）和C档位（模型A已经有），就能先
   实测这套流程设计得对不对，可以跟前面几步并行推进
