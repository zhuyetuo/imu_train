# 两阶段RF架构——行为严重度(模型A) + 综合严重度(模型B)

> 回答"S要不要单独一个RF，还是跟C合一个RF"这个问题。结论：**两个模型**，
> 但理由是数据可得性的工程约束，不是照搬PM的C/S两层设计——两个模型内部
> 都不用PM的加权公式，权重都是从真实标签训练出来的。

## 1. 为什么是两个模型，不是一个

核心原因：**两类特征到达的时机不一样**。

- IMU/行为特征（`rf_feature_spec.md`）——每天自动都有，不需要用户做
  任何事
- 问答特征（`questionnaire_feature_spec.md`）——只有用户填了问答才有，
  是稀疏的、事件触发的

如果只用一个模型，那这个模型每天都要预测，但大部分天问答特征都是缺失的
——虽然`HistGradientBoostingClassifier`能处理缺失值，但这样设计出来的
单一模型，本质上退化成"平时几乎只靠IMU特征判断，偶尔有问答数据时用一下"，
没有真正发挥问答信息的价值，而且没法回答一个实际的产品需求：**IMU信号
异常时，要能立刻给用户一个初步严重度判断，不需要等用户先填完问答**。

拆成两个模型能同时满足两种场景：
- 平时（没有问答）：模型A单独就能给出一个基于行为的严重度判断，反应快
- 问答触发之后：模型B综合行为+问答信息，给出更完整的严重度判断

## 2. 架构

```
IMU/行为特征（rf_feature_spec.md）
        │
        ▼
   【模型A】行为严重度分类器
   HistGradientBoostingClassifier
   输出：三档概率 P(轻/中/重)，或简化成一个连续的"行为异常分"，映射到C0/C1/C2
        │
        ├── C0：不触发问答，S直接不评（或者也可以定义成S0，看产品要不要
        │        展示"S暂无数据"这种状态，见第2.1节）
        │
        └── C1或C2：触发问答，弹给用户
                │
                ├── 用户不回答 → **直接给S1**（不管当时是C1还是C2，
                │                  都是S1，见第2.1节的说明和待确认点）
                │
                └── 用户回答了 → 走模型B
                        │
                        ▼
        IMU/行为特征 + 模型A输出 + 问答特征（questionnaire_feature_spec.md）
                        │
                        ▼
                【模型B】综合严重度分类器
                HistGradientBoostingClassifier
                输出：真实预测的S0/S1/S2（不是固定给S1）
```

模型B的输入 = 模型A能看到的全部特征 + 模型A自己的输出（概率或分数）+
问答特征——这是标准的**stacking（模型堆叠）**架构，模型B相当于在模型A
的判断基础上，看有没有额外的问答信息可以修正/补充，权重完全靠训练学出来，
不是"模型A的结果打4折，问答打6折"这种预设比例。

### 2.1 触发条件与未回答兜底逻辑（已确认）

- **触发条件**：模型A输出达到C1及以上（C1或C2）才弹问答给用户，C0不触发
  ——跟SBS现在C0/C1/C2的定义对齐，正常范围内不打扰用户。
- **用户不回答**：直接给**S1**，不区分当时触发问答的是C1还是C2。
- **用户回答了**：不再是固定值，走模型B算出真实的S0/S1/S2。

**这个兜底规则有一点需要明确指出**：如果触发时C已经是C2（模型A判断的
最严重档），但用户没有回答问答，兜底给的是S1，而不是S2——也就是说
"不回答"这个结果，展示出来的严重度**比模型A单独判断的还要轻**。这是
不是符合产品预期，建议明确确认一下：是不是故意设计成"没有问答信息时，
不给用户看最高级别的警示，避免在信息不全时过度报警"，如果是，这个逻辑
没问题；如果只是还没考虑到这个情况，可能需要重新设计成"不回答时至少
不比C的判断更轻"（比如不回答时展示"C2，S信息缺失"，而不是直接展示
"S1"这种听起来比C2更轻松的结果）。这个点不影响模型架构本身，但会影响
用户看到的最终展示逻辑，建议跟产品侧过一遍。

## 3. 两个模型分别怎么训练/评估

| | 模型A（行为严重度） | 模型B（综合严重度） |
|---|---|---|
| **输入特征** | `rf_feature_spec.md`全部 | 模型A的输入 + 模型A输出 + 问答特征 |
| **训练样本粒度** | 每(狗,天)一条，每天都有 | 只有(狗,天)有问答记录的那些天才有样本，天然比模型A的训练集小很多 |
| **标签来源** | 真实兽医评估（跟`daily_skin_report.py`日报对照积累的那批） | 同样是真实兽医评估，但因为问答是稀疏的，能配对上"当天有问答+当天有兽医评估"的样本更少，训练进度会比模型A慢 |
| **上线时机** | 更早——不依赖问答，标签攒够就能训 | 更晚——既要等模型A稳定，也要等问答数据+对应兽医标签攒够 |
| **评估方式** | `GroupKFold`按狗分组，宏F1+校准曲线（`rf_feature_engineering_plan.md`已定） | 同样的评估框架，但样本量小的阶段结果方差会更大，解读时要注意 |

## 4. 训练顺序建议（呼应`deployment_plan_2026.md`的节奏）

1. **先训模型A**，用现有的IMU特征+真实兽医日报标签，这个不依赖问答，
   数据积累速度最快，按`algorithm_engineering_plan.md`的前中期节奏推进
   （稳健Z分数/CUSUM打底，标签够了升级到监督模型）。
2. **问答功能上线后**，开始积累"问答+同期兽医评估"的配对数据，同时把
   模型A的输出接进特征管道，为模型B做准备。
3. **模型B比模型A晚启动是正常的**，不用因为问答数据少就着急拿模型A的
   逻辑去凑一个"综合分"（那样又会退回到手工公式的老路），宁可模型B
   晚一点上线，也要等真实数据支撑。

## 5. 跟PM原始C/S设计的对应关系（仅供理解，不是要复刻）

PM的C大致对应模型A（都是纯行为信号），PM的S大致对应模型B（都是行为+
问答综合），**这个对应关系只是帮助理解两边在说同一类东西，不代表模型B
要去拟合/复刻PM那个"C×40%+问答×25%×2"的具体公式**——模型B的目标是
直接学习"真实兽医综合评估"这个标签，不是学习"PM设计的分数公式算出来
的数字"，这是两个不同的训练目标，后者本质上还是在拟合一个人为规则，
没有跳出SBS当初的问题。
