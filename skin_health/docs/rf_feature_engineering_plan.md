# RF特征工程方案——从前期到后期一以贯之

> 回答"现在前期就想用RF，特征该怎么设计"这个问题。核心思路：**特征工程和
> 训练/评估框架现在就能定型并跑通（这部分不需要标签），但RF模型本身现在
> 没法真正训练/验证（RF是监督模型，需要兽医真实标签，现在几乎没有）**。
> 用固定不变的特征schema贯穿前中后期，随着标签量增长同一套pipeline反复
> 训练评估，学习曲线（标签量 vs 效果指标）本身就是回答"这个特征集/这个
> 数据质量的项目上限在哪"的答案。

## 1. 现在到底能做什么、不能做什么

**能做**：
- 把`daily_features()`之类的特征提取代码，升级成一个**唯一的、版本化的特征
  计算函数**——`compute_feature_vector(dog_id, date) -> dict`，训练和线上
  推理（`daily_skin_report.py`）都调这一个函数，避免"训练时算法特征的方式"
  和"线上算特征的方式"不一致这种经典ML工程事故（train/serve skew）。
- 把训练/评估框架搭起来：数据切分方式（按狗分组，不能按行随机切，同一只狗
  的数据不能同时出现在train和test）、评估指标（AUC/宏平均F1/校准误差）、
  交叉验证方式（`GroupKFold`），这些现在就能定好、写好代码，不用等标签。
- 用`scenario_gallery.md`那10个合成场景（有已知的"应该是C0/C1/C2"标准答案）
  跑一遍RF pipeline，**验证的是代码本身没bug**（管道跑得通、特征算得对、
  评估流程能出结果），不是验证真实准确率——跟SBS当初只用合成数据验证是
  同一个局限，不能拿这个结果当"模型已经验证过"的证据。

**不能做**：
- 现在没有真实标签，没法回答"这个特征集实际预测准不准"——这个问题9月
  开始有兽医标签之后才能真正回答，学习曲线要等真实数据才能画。

## 2. 特征清单（RF专用视角，基于`feature_catalog.md`重新组织）

跟`feature_catalog.md`的区别：那份是给贝叶斯模型选似然分布用的（区分计数/
连续/比例类型），这份是给RF挑特征、标注"哪些第一天就能算、哪些要等数据积累"、
以及RF specific的工程注意事项。

| 类别 | 特征 | 何时可用 | RF专用备注 |
|---|---|---|---|
| **频率** | `event_count` | 第1天 | |
| | `event_rate_per_wear_hour` | 第1天 | **必须算这个**，RF不像GLM能用offset/exposure处理佩戴时长，佩戴时长不同的两天次数不可比，必须显式换算成"每小时次数"这种比率特征喂进去 |
| **时长** | `total_duration_min`、`duration_rate_per_wear_hour` | 第1天 | 时长同样要换算成比率版本，原因同上 |
| | `duration_mean`/`duration_median`/`duration_max`/`duration_std` | 第1天 | |
| **时间分布** | `night_ratio` | 第1天 | |
| | `hour_histogram`(24维) | 数据量大之后 | RF不像线性模型那样怕高维共线性，但小样本下24维还是会稀释重要特征的分裂机会，先不加，等标签数到几百再考虑 |
| **聚集/模式** | `interval_mean`、`interval_std` | 第1天 | 直接喂原始统计量，**不要**只喂`cluster_count`这种人为阈值二值化后的版本——把"1小时≥5次算聚集"这种规则交给RF自己从`interval_std`里学分裂点，比预先手工二值化保留更多信息，这是用ML思维替代SBS手调阈值的具体体现 |
| **睡眠/行为影响** | `sleep_interrupt_count` | 第1天 | 用计数版本，不要同时加二值版本（`sleep_interrupt`），两者高度冗余，RF没有获得额外信息，纯粹多一个没用的分裂候选 |
| | `activity_duration`/`sleep_duration` | 第1天 | 同一个3分类模型的背景类别输出，作为环境背景特征 |
| **基线/趋势** | `rolling_mean_3d`/`7d`/`14d` | 需要3/7/14天历史，不足时留空 | **必须做缺失值处理**（见下面第4节），`RandomForestClassifier`不像`HistGradientBoostingClassifier`能原生吃NaN |
| | `baseline_ratio`、`baseline_delta_abs`、`z_score_vs_self` | 需要基线建立(≥7天) | 同上，缺失值要显式处理 |
| **数据积累程度** | `history_days_available`（新增） | 第1天（值本身就是"到今天为止攒了几天数据"） | **这是替代SBS现在`bootstrap_mode`硬编码分支的关键特征**——不再手工写"不满21天走另一套逻辑"的if/else，直接把"到今天有多少天历史"当一个连续特征喂给RF，让模型自己学习"数据越少，这些基于历史的特征越不可信、应该更依赖绝对值特征"这个关系，这才是真正的机器学习思维，不是又发明一套新的硬编码规则 |
| **品种/群体** | `breed_or_size_class`（类别特征） | 第1天（品种信息本来就有） | sklearn的`RandomForestClassifier`处理类别特征需要one-hot或者target encoding，品种数不多时one-hot没问题 |
| | `breed_baseline_rate`（品种层期望值） | 需要BHM或至少品种内统计有意义（中期起） | 中期BHM先验算出来之后可以直接当一个特征喂给RF，呼应`algorithm_engineering_plan.md`里"后期GBM吸收多信号源"的思路，RF/GBM都适用 |
| **元信息（非预测特征）** | `valid_wear_hours` | 第1天 | 只用来算比率特征的分母，不直接当预测特征喂（佩戴时长本身跟皮肤健康没有因果关系） |
| | `data_quality_flag` | 第1天 | 数据不够好的天（`insufficient`）直接从训练集剔除，不是当特征喂 |

## 3. 训练/评估框架（现在就要定型的部分）

1. **数据存储**：跟`deployment_plan_2026.md`里提的"按狗持续累积历史"是
   同一件事——每天一行，dog_id/date/上面这些特征/兽医标签（暂时可能是空的），
   append-only，不要每次重新生成。
2. **切分方式**：`GroupKFold`，按`dog_id`分组，同一只狗的数据不能同时出现
   在train和test——这是最容易踩的坑，同一只狗不同天的数据天然相关（同一只
   狗的基线、品种、个体习惯都固定），随机按行切分会导致过于乐观的评估结果，
   看起来准实际部署到新狗身上会明显变差。
3. **评估指标**：主指标用**宏平均F1**（C0/C1/C2类别不平衡，C2大概率是少数
   类，准确率会被大多数的C0淹没），辅助看**校准曲线**（预测概率是不是真的
   对应实际发生率，医疗场景这个比纯排序能力更重要）。
4. **超参数保守起步**：小样本阶段`max_depth`控制在3-5、`min_samples_leaf`
   设5-10、`class_weight='balanced'`（应对类别不平衡），不要一上来就用
   默认的不限深度设置，小数据量下极容易过拟合、每次重训结果都不稳定。
5. **概率校准**：RF的`predict_proba`原始输出经常没有很好的校准性，标签量
   够用之后（几十条起）用`CalibratedClassifierCV`包一层。
6. **学习曲线追踪**：每次标签量有明显增长（比如每月）就重新训练评估一次，
   把"标签量 vs 宏F1/校准误差"画成曲线存下来——这条曲线**自然收敛到的水平
   就是当前特征集在当前数据质量下的项目上限**，如果曲线在某个标签量之后
   明显不再提升，说明瓶颈在特征而不在数据量，该回去加特征/改特征而不是
   继续攒更多同质的数据。

## 4. 缺失值处理（RF专用，容易被忽略的细节）

`sklearn.ensemble.RandomForestClassifier`**不支持NaN输入**（跟
`HistGradientBoostingClassifier`不一样，后者原生支持缺失值当成一个分裂
方向）。基线/趋势类特征在个体历史不足时天然是NaN（比如`rolling_mean_14d`
在第5天时没法算），处理方式两选一：

- **方案A（推荐）**：换成`HistGradientBoostingClassifier`而不是
  `RandomForestClassifier`——sklearn自带、原生支持缺失值、不需要额外插补
  逻辑、大数据量下通常比RF效果更好也更快，本质上是轻量版GBM，正好也是
  `algorithm_engineering_plan.md`里后期要上的方向，现在直接用等于前期
  后期用同一套代码，不用来回切换实现。
- **方案B**：坚持用RandomForest，则需要显式插补——用一个明显超出正常范围
  的哨兵值（比如-1）+ 配一个"是否为缺失"的二值伴随特征（`rolling_mean_14d`
  + `rolling_mean_14d_is_missing`），让树自己学会"看到哨兵值就走另一条
  分裂路径"，不要用均值/中位数填补（那样会人为制造假的"正常"信号）。

如果不确定选哪个，建议直接用**方案A**——`HistGradientBoostingClassifier`
本身就是`algorithm_engineering_plan.md`后期要上的方向（GBM家族），现在
就用它，前中后期都不用换模型实现，只是随着数据量增长逐步放开超参数
（加深、加树、加特征），比RF更符合"一以贯之用到后期"这个诉求。

## 5. 一句话总结

现在（8月）能做、该做的：把上面这套特征schema和训练/评估框架代码写出来、
用合成场景数据跑通（验证代码没bug，不是验证准确率）；9月第一批真实标签
一到，立刻能用；不需要等到"数据攒够了再开始搭框架"，框架和特征工程本身
不依赖标签，标签只是喂给已经搭好的管道。模型实现建议直接用
`HistGradientBoostingClassifier`而不是传统`RandomForestClassifier`，
省掉缺失值处理的麻烦，还跟后期GBM方向天然衔接，不用中途换实现。
