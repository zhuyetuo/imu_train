## 一、C值（IMU行为严重度，0-100分，权重40%）

**结论：`skin_health/code/scratch_burden.py`的SBS引擎已经是这份PM规则的
精确1:1实现，逐项核对完全一致，不需要改代码。**

| PM规则项 | PM的具体数值 | scratch_burden.py对应实现 | 核对结果 |

**备注1（分母保护值）**：PM文档写"分母最低按3计算"，`scratch_burden.py`
里`BASELINE_DENOM_FLOOR=1`——两者不一致，但这个差异只在基线值极低
(0/1/2)时才会体现出来，且`scratch_burden.py`的代码注释明确写着
"只为避免除以0，不是用来压低低基线狗信号的"，是有意的设计选择，不是
疏漏。要不要改成3以完全对齐PM文档，需要跟算法组确认，这份文档先如实
记录这个差异，不擅自改。

**备注2（7个举例验证）**：PM文档"变化幅度"部分给了7个具体计算举例
（2→4次判0分、2→6次判5分、2→12次判20分、5→15次判20分、5→20次判20分、
30→35次判0分、30→46次判20分、15→46次判30分触发红旗），逐个代入
`_DELTA_TIERS`的判定逻辑验证，结果全部吻合，不再赘述每一个的推演过程。

**备注3（2026-08更新，发现一处C档位判定的规则缺口）**：PM文档举例七
原文是"满足显著变化条件5，得分30分。**触发红旗信号，直接进入C2**"——
也就是说变化幅度这一项自己触发红旗时，这一天应该**直接判C2**，不是
"红旗项封顶30分，再跟其他三项加总、按30/50阈值走"。如果只封顶不直接
定档，举例七这种"只有变化幅度红旗、其他三项都是0分"的情况，总分只有
30，按阈值只会判成C1，跟她原文明确写的"直接进入C2"矛盾。

`pm_skin_scoring/code/questionnaire_app.py`里新增的"C值计算"标签已经
按"任意一项触发红旗就直接判C2"实现，用举例七验证过（总分30分，但因为
红旗，正确判定C2）。

**但`skin_health/code/scratch_burden.py`的`score_day()`目前没有这条
规则**——那边红旗只把对应那一项的分数封顶(比如`delta_score = 30`)，
最终还是按`total>=50`/`>=30`的阈值走，不会因为某一项红旗就直接跳到
C2。这是本次核对新发现的一处遗漏，**需要跟算法组同步确认要不要修
`scratch_burden.py`**，这份文档先如实记录，不擅自改那边的代码。

**备注4（2026-08，修复"变化幅度"红旗误判的bug）**：`compute_c_score()`
早期实现里有一处逻辑错误——判定"变化幅度"红旗时直接看`相对基线比值>3`
这一个条件，没有同时要求绝对增量也达到tier5的门槛(≥20次或≥15分钟)。
PM文档的tier5本来是"绝对增量和相对倍数同时满足"才给30分/红旗，基线值
很小时相对倍数很容易超过3倍但绝对增量根本够不到门槛——用户举的实测
例子：基线1次/2分钟，当天10次/12分钟，时长相对倍数=12÷3(分母保护)=4倍
(>3)，但时长绝对增量只有10分钟，够不到tier5要求的≥15分钟，应该落在
tier4(得20分)，之前的代码却因为"倍数>3"这一个条件就把分数强改成30分、
还触发了红旗，多算了10分、且红旗是假的。

修复：红旗判定改成直接看`_c_delta_score_one()`按双门槛算出来的分数
是不是真的等于30(而不是额外拿相对倍数单独判一次)，跟tier表本身的判定
逻辑保持一致，不再有独立于tier表之外的"倍数>3就强制30分"这条隐藏规则。
用户举的例子验证过：修复后正确得20分，不再触发假红旗。

**这个bug只在`pm_skin_scoring`这边，不影响`scratch_burden.py`**——那边
`score_delta()`本来就没有这种"单独按倍数判红旗"的逻辑，红旗判定是外层
`score_day()`里`delta_detail.get("ratio", 0) > 3`这一行，跟这边是类似
的潜在风险点(相对倍数>3但绝对增量不够tier5门槛时可能误判)，但没有被
本次用户的例子触发验证，暂不确认是否有同样的bug，先记录在这里，需要
时再单独核对。

**备注5（2026-08，中断影响门槛更新，PM文档修订版）**：PM原文档口误，
"变化幅度"表格右侧举例算出来是30分，但对应档位标题写的是20分，PM确认
后修正为30分（跟举例数字对齐），同时跟兽医同事重新讨论后调整了"中断
影响"这一项的门槛：

| 项目 | 旧版 | 新版(2026-08) |
|---|---|---|
| ZD多少分算20分 | `ZD==1` | `ZD<3`（即ZD是1或2都算20分） |
| ZD多少分算30分/红旗 | `ZD≥2` | `ZD≥3` |
| ZD和长时间抓挠的关系 | 原文写"同时满足" | 修正为"满足一项即可"（其实
  代码这边一直是OR不是AND，跟旧版代码没有实质冲突，只是PM原文字面表述
  之前写错了，这次一起对齐说清楚） |

`pm_skin_scoring/code/questionnaire_app.py`的`_c_score_interruption()`
已经按新版门槛改好。**`skin_health/code/scratch_burden.py`的
`score_interruption()`还是旧门槛(`zd>=2`)，没有跟着改**——这是PM原方案
本身的规则修订，不是bug，需要跟算法组同步是否要把`scratch_burden.py`
也改成新门槛，这份文档先如实记录，不擅自改那边的代码。

**备注6（2026-08，修复相对倍数边界判断的bug）**：PM表格里"相对倍数"这一栏
写的是"1.3倍<相对倍数≤1.5倍"这种——下限用`<`(不含)、上限用`≤`(含)，只有
最高档"相对倍数>3倍"没有上限、纯大于；但"次数/时长最小绝对增加"这一栏
写的是"≥"(下限含)。两栏边界含义不一样，`_c_delta_score_one()`之前两个
条件统一用`>=`判断，导致倍数刚好等于某档下限的整数边界值时(用户实测例子：
基线30次→今日90次，比值刚好3.00倍)会被错误地算进上一档——3.00倍按PM表格
该落在"2倍<相对倍数≤3倍"这档(20分)，之前的代码却因为`ratio>=3.0`判定成
命中最高档(30分+红旗)，多算10分还多触发一个不该有的红旗。

修复：绝对增加的判断保持`>=`(表格写的就是"≥")，相对倍数的判断改成`>`
(严格大于，表格写的是"<...≤"这种下限不含的区间)。用户举的例子(30→90次，
比值刚好3.00)验证过：修复后正确落在20分那档，不再误触发红旗；边界值
1.5倍(基线10→今日15次)也验证过，正确落进tier2(5分)而不是tier3(10分)。
举例七(15→46次，比值3.07真正大于3)回归测试确认没有被误伤，还是正确
判30分/C2/红旗。

**这个bug只在`pm_skin_scoring`这边，`skin_health/code/scratch_burden.py`
的`_delta_score_one()`有相同结构的`ratio >= ratio_min`判断，可能有一样
的边界问题，但没有被本次用户的例子直接验证，暂不确认，先记录在这里，
需要跟算法组同步核实、决定要不要一起改。**

## 二、S值（综合严重度，问答部分权重60%）

**结论：`pm_skin_scoring/code/questionnaire_app.py`已按下面公式实现，
用PM文档给出的满分示例(74.25分)做过精确验证。**

```
S总分 = C值(0-100) × 40%
      + 皮肤状态组原始分小计(皮肤颜色+体味+皮损) × 35%
      + 毛发状态组原始分小计(秃毛部位+秃毛面积+整体毛质) × 25%
```

组内原始分直接相加，不做归一化处理，再乘以组权重——这个是跟用户
确认过的公式形式（见对话记录），不是自己猜的。

**验证用例**（PM文档原文"总分74.25分=100×0.4+55×0.35+60×0.25"）：

```python
compute_score(
    c_value=100, has_hair_loss="是",
    color="C. 明显鲜红，但还没有破皮。",              # 15分（皮肤颜色单项最高分，不是满分表里的20——PM这题满分就是15）
    odor="D. 一进屋或者离得很远，就能闻到恶臭。",       # 20分
    lesion="D. 有糜烂、液体、结痂、脓包、红疙瘩，或者皮肤裂开。",  # 20分
    hair_spot="D. 脱毛连成一大片，不是零星小块。",      # 20分
    hair_diameter="D. 最大的一块超过3cm，面积比较明显。", # 20分
    coat="D. 大部分毛发都明显干枯、易断、毛质很差。",    # 20分
)
# 皮肤组=15+20+20=55（跟PM举例的55完全对上）
# 毛发组=20+20+20=60（跟PM举例的60完全对上）
# S总分 = 100*0.4 + 55*0.35 + 60*0.25 = 40 + 19.25 + 15 = 74.25
# 实测输出: 74.25 ✅ 精确匹配，不是近似值
```

## 三、发现并修复的问题：Python内置round()的银行家舍入

第一版实现用`round(total, 1)`，`round(74.25, 1)`在Python里实际算出
`74.2`（不是`74.25`四舍五入后的`74.3`），因为Python的`round()`是
round-half-to-even（银行家舍入），不是标准四舍五入——这跟
`skin_health/docs/rf_synthetic_validation_findings.md`里记录过的同一个
坑完全一样（那边是合成数据标签生成踩过的），这次在S值计算这里又踩了
一次，说明这是个值得记住的通用陷阱，不是偶然。

修复：用`_round_half_up()`（`math.floor(x*10**n+0.5)/10**n`）代替
Python内置`round()`，验证`_round_half_up(74.25, 2)`精确等于`74.25`，
不再丢失/错误舍入这个精度。同时把S总分的显示精度从1位小数改成2位
小数——1位小数本身就会丢失PM文档举例里"74.25"这种精确到分的数字。

## 四、S档位边界（已由PM确认，2026-08更新）

之前版本的文档带"+"号（"0≤S<12+"这种），含义不确定，且"≤70"上限
跟74.25满分示例矛盾，已标注为待确认。PM后续发来确认版，边界精确
数值如下，页面上的"⚠️待确认"警示已经去掉：

| 档位 | 边界 |
|---|---|
| S0 | 0 ≤ S < 12 |
| S1 | 12 ≤ S < 20 |
| S2 | 20 ≤ S ≤ 74.25 |

`74.25`正好是公式本身的理论最大值（C=100×40%+皮肤组满分55×35%+
毛发组满分60×25%），S2这一档不需要单独设上限，公式自身就封顶在这，
不再是之前那个自相矛盾的"≤70"。

**另外确认版还带出一条红旗规则**："信号细节单项打分为20分时，直接
触发S2"——体味/皮损/秃毛分布/秃毛面积/整体毛质这5道题满分都是20分
（皮肤颜色满分只有15，够不到这条规则），只要有任意一题选到了满分
选项，不管加权总分算出来是多少，直接判S2，不看总分高低。已实现在
`compute_s_total()`的`red_flag`判断里，跟C值那边"红旗信号触发直接给
C2"是同一类"某个维度已经严重到可以跳过加权总分直接定档"的设计，
逻辑上是一致的。

验证用例：`odor="D. 一进屋或者离得很远，就能闻到恶臭。"`（体味20分）
+ 其余题目全选最低档，C值=0——加权总分只有7分（远低于S1的12分下限），
但因为体味这一项是满分20，红旗规则生效，最终判定`S2`，不是`S0`。

## 五、页面拆成三个独立标签（2026-08更新）

用户要求"填写问答"标签不再改动，C值/S总分单独拆成新标签，各自确认
好再看最终结果。改动后的结构：

- **填写问答**：跟C值追加之前的版本完全一样，`compute_score()`签名/
  输出/保存逻辑都没变，`RECORD_COLUMNS`也是原来那12列，不含C值/S总分
- **C值计算**（新增）：结构化输入(基线次数/时长、今日次数/时长、
  聚集时段数、持续天数、ZN/ZD/是否长时间抓挠)算C值，不需要接原始
  抓挠事件时间戳，是PM四项C值规则的独立复刻，跟"一、C值"这节核对的
  规则用的是同一套（包括这次新发现的红旗直接定档规则）
- **S总分**（新增）：读"填写问答"标签里已经选好的答案（复用
  `_question_group_scores()`共用函数，两个标签用的是同一套计算逻辑，
  不会得出两个不一致的问答分数）+ 自己填的C值（也可以从"C值计算"标签
  自动同步过来，不用手动抄），组合出最终S总分/S档位
- **历史记录**：不变，还是只存"填写问答"标签的记录

三个标签之间的C值同步：C值计算标签算完后，通过Gradio组件的`.change`
事件自动把结果写进S总分标签的C值输入框，不需要用户手动把数字抄一遍；
但S总分标签的C值输入框本身也保持可编辑，用户也可以跳过C值计算标签、
直接手动填一个C值进S总分标签（比如C值是从别处已经算好、直接抄过来的
情况）。
